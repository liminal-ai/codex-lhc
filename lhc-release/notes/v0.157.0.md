# Codex + LHC v0.157.0

Codex-LHC 0.157.0 is upstream Codex 0.157.0 (`rust-v0.157.0`, peeled commit
`00c972ed5d`) with the LHC integration carried forward. The LHC core is
unchanged from 0.156.1 (pin `47e360a3`), and LHC thread records are not
migrated. Codex's own thread-history database is migrated, one way, the first
time 0.157.0 opens it: **back it up before upgrading** (see below).

## Before you upgrade

Close Codex, then copy `~/.codex/thread_history_1.sqlite` together with its
`-wal` and `-shm` files if present (under `$CODEX_HOME`, or `$CODEX_SQLITE_HOME`
if you set either). That copy is the only way back to 0.156.1; the installer
does not make one.

## From upstream 0.157.0

GPT-6 Sol and Luna in the model catalog, a network policy for sandboxed
commands and MCP servers, a fullscreen transcript by default, and other TUI and
app-server changes. See the
[upstream release](https://github.com/openai/codex/releases/tag/rust-v0.157.0).

## What we changed to integrate it

- **Background server stays off.** Upstream 0.157.0 starts a shared background
  app-server by default. Codex-LHC keeps it off, so Codex runs in-process as in
  0.156.1. You can opt in with `features.daemon_auto_start = true`, but that
  mode has not been tested with LHC.
- **Guardian now uses thread-owned history by default.** Upstream turned this
  on in 0.157.0; in 0.156.1 it was off unless you enabled it. Codex-LHC's code
  that carries Guardian's history across an LHC compaction and a reopen now
  runs for everyone, and was fitted onto upstream's rewritten reopen logic.
  To go back to 0.156.1's behaviour, add to `config.toml`:

  ```toml
  [features.guardianv2]
  thread_context = false
  ```
- **LHC compactions record resume data.** Upstream 0.157.0 reopens a thread
  from its latest compaction using data it now saves with each compaction. LHC
  compactions save the same data, so reopening an LHC thread takes that path
  instead of an older fallback.
- **Database migration renumbered.** Upstream's new thread-history migration
  took number 7, which Codex-LHC already used. Ours is now 8, and on first open
  the existing row is relabelled automatically (from 7 on 0.155.1 and 0.156.1
  installs, or 5 on older ones) before upstream's 7 is applied.
- **Hand merges.** 21 files changed on both sides and were merged by hand,
  mostly session and turn handling, reopen-after-compaction, compaction records
  and the database migrations.

## Where problems are most likely

These are the areas with new or hand-merged code and the least real-world use.
If something goes wrong after upgrading, it is most likely here.

1. **Reopening a thread after a compaction.** Upstream rewrote this logic and
   Codex-LHC's pieces were fitted onto it. A problem would show as missing or
   repeated history after reopening a thread.
2. **Guardian on thread-owned history.** The carry-over code had only run in
   tests before this release. In the live run, Guardian's review after a
   compaction and again after a kill-and-reopen listed the retained
   conversation once each time, with no repeated entries. Known case: when a
   subagent's reply is in the recent part of the conversation at a compaction,
   older recent messages can appear twice in what Guardian reviews against.
   Not seen in use.
3. **The first open after upgrading.** The migration relabel runs once per
   install. If it goes wrong, Codex cannot open its thread history; restore
   your backup and reinstall 0.156.1.
4. **GPT-6 Sol and Luna.** LHC compaction on GPT-6 Sol and Luna has not
   been tested. The live tests ran on GPT-6 Astra (the default), with LHC
   summaries on GPT-5.6 Luna.
5. **Upstream's network policy.** Not exercised by the live tests: the test
   machine's sandbox cannot create user namespaces, so every command ran
   outside the sandbox after a Guardian-reviewed approval (0.156.1 behaves the
   same there). Background summaries completed and the Code Mode host ran
   every tool call with no policy errors logged, but the policy itself is
   covered only by upstream's tests.

## Known limitations (carried from 0.156.1)

- Threads rewound under 0.155.1 or earlier can surface rewound turns via
  retrieval and after compaction. Native rewind never removed those turns from
  the LHC record, and this release does not rewrite them away.
- Esc, Esc now opens upstream's transcript browser. Choosing a prompt there
  to rewind an LHC thread is refused with `Rewinding is not yet supported.`
  and the prompt is left in the composer to edit and resend.
- Quitting Codex or pressing Ctrl-C while a background summary is starting can
  leave that summary failed. That stretch of the conversation then shows as an
  excerpt instead of a summary.
- Background work that finishes after a compaction logs "unknown turn"
  warnings. The results still arrive.

## Rolling back to 0.156.1

1. Close Codex.
2. Restore the `thread_history_1.sqlite` backup (with its `-wal`/`-shm`
   files). 0.156.1 refuses the migrated database.
3. Reinstall 0.156.1 (`install.sh --version 0.156.1`, or point `current` back
   at the retained 0.156.1).

LHC thread records need nothing. Threads written by 0.157.0 open on 0.156.1; the
extra resume data is ignored (checked with a 0.157.0 compaction and a fresh
thread-history database).

Releases v0.150.2 and earlier cannot reopen migrated LHC threads. See
[upgrade details](lhc-docs/INSTALL.md#upgrade-and-compatibility).

## Qualification

Upstream base `00c972ed5d`, LHC core pin `47e360a3`. The five-platform
candidate run and the byte-check of its artifacts are recorded in this
release's approval record, not here.

- **Local gates.** The fork's tripwire script (hook count, reviewed
  native-routing ignores, release helpers, compile, bare `exec` capture,
  mid-turn parts, host library and certification suites, capture seam, compact
  bridge and arm, mid-turn, full loops, app-server startup, fmt, clippy,
  goldens, patch drill at the upstream base, slice D, pin, vendor clean) is
  green on the release commit. Two layers had timed out once under a parallel
  release build; both passed twice on a quiet machine.
- **Migration and rollback rehearsal** on a copy of a real 0.156.1 home
  (thread-history database with 524 projected threads, a live rollout with
  nine compactions): first open relabelled the fork row and applied upstream's
  migration; the thread reopened and answered. 0.156.1 then refused the
  migrated database with `migration 7 was previously applied but has been
  modified`; after restoring the backup it reopened the thread and answered.
  A rollout with a 0.157.0 compaction opened on 0.156.1.
- **TUI, real model (GPT-6 Astra).** Subagent review, `/compact`, prompt,
  Guardian-reviewed approval, second `/compact`, recall of turn-1 facts after
  both folds, SIGKILL, `codex resume`, prompt, Guardian-reviewed approval after
  the reopen, `codex exec resume`. Rebuilt user messages carried `msg` ids
  only; no provider rejections; no `unknown turn` warnings; all 55 background
  summaries completed. Guardian's review transcripts after the fold (13
  entries) and after the reopen (69 entries) listed each item once.
- **App-server (what the t3code seats run).** `thread/start`, two turns,
  `thread/compact/start` (the fold completes as a compaction turn; no
  `thread/compacted` notification is sent, same as 0.156.1), recall after the
  fold, `thread/revert` refused with `Rewinding is not yet supported.`, new
  process, `thread/resume`, recall again. The same sequence on installed
  0.156.1 behaved identically.

## Packages

The five native archives (Linux x86-64/ARM64, Windows x86-64/ARM64, Apple
Silicon macOS) keep the canonical Codex package layout. Every package contains
Codex, Code Mode host, bundled ripgrep, canonical metadata, and LHC
provenance. Linux packages also contain bwrap and patched zsh; Windows
packages contain the command runner and sandbox setup helpers.
